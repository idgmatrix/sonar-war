# SSN-X 소나 시뮬레이터 — 개발 계획

> 근거 문서: `근미래 전술 잠수함 소나 시뮬레이터 시스템 설계 명세서.md`, `WebRTC 기반 1_1 멀티플레이 구조.md`, `멀티플레이 버전 개발 지침.md`

## 1. 목표와 원칙

- **최우선 제품 목표:** 해저에서 들릴 수 있는 각종 소리를 가능한 한 물리적으로 그럴듯하게 합성한다. 게임 플레이와 시각 UI는 DSP 결과를 관찰하고 활용하기 위한 상위 계층이다.
- **사실성 확보 방식:** 청감만으로 임의 조정하지 않고, 공개 측정 자료·표준·논문·제조사 자료에서 소스와 환경 파라미터를 수집하여 단위, 기준 조건, 출처, 불확실성을 함께 관리한다.
- **플랫폼:** 웹 브라우저 (데스크톱 우선). 별도 게임 서버 없음 — 멀티플레이는 WebRTC P2P.
- **핵심 원칙 (개발 지침 문서):**
  1. 모든 잠수함/표적은 동일한 `AcousticEntity` 데이터 구조. "누가 조종하는지" 엔진은 모른다.
  2. 센서/렌더 파이프라인은 `AcousticEntity[]`만 받는다.
  3. `exportState()` / `importState()`를 **첫날부터** 구현해 둔다.
- **점진 빌드업:** 싱글 플레이 완결 → 직렬화 검증 → WebRTC 결합. 멀티플레이는 후반부(마일스톤 M8)에 얹는다.
- **Web Audio 역할 제한:** 출력 장치 연결, 게인·라우팅·후처리만 담당한다. 음향 소스와 전파 효과의 합성은 Rust/WASM DSP에서만 수행한다.

### DSP 계층 경계

```text
Source Model → Propagation Channel → Receiver / Array → Analysis / Output
 발생원 자체     매질·거리·경계 효과       센서·플랫폼 효과       표시·재생
```

- **Source Model(발생):** 거리, 수심 음속 구조, 센서 방향을 알지 않는다. 축/블레이드/기계류 선 스펙트럼, 캐비테이션, 생물음처럼 발생원 자체의 신호만 생성하며 출력은 기준 거리의 음압 또는 소스 레벨(`dB re 1 µPa @ 1 m`)로 정의한다.
- **Propagation Channel(전파):** 거리 감쇠, 주파수별 흡수, 음속 구조, 도플러, 표면·해저 반사와 다중 경로 등 매질과 기하에 따른 변형을 담당한다.
- **Receiver / Array(수신):** 하이드로폰 감도/주파수 응답, 배열 지연, 빔포밍, 자함 소음·유동 소음과 수신기 특성을 담당한다. 물리 음압에서 현재의 `1 Pa = 1,000,000 µPa = 1.0 FS`(`120 dB re 1 µPa`) 출력 규약까지의 교정도 이 계층에 둔다.
- **Analysis / Output(분석·출력):** BASS/LOFAR/DEMON 분석과 화면·헤드폰 출력을 담당하며 새로운 음향을 합성하지 않는다.
- 동일한 원시 소스 신호를 여러 환경과 수신기 설정에 재사용할 수 있어야 한다. 계층 간 파라미터 누출은 인터페이스 테스트로 차단한다.

## 2. 기술 스택 결정

| 영역 | 선택 | 비고 |
|---|---|---|
| 언어 | **TypeScript** (게임/UI/시뮬레이션) + **Rust** (DSP 코어) | 물리/수학 코드가 많으므로 타입 안전성 필수. DSP는 Rust에서 사실적 음향 생성 |
| 빌드 | **Vite** (TS) + **wasm-pack/cargo** (Rust → WASM) | dev: cargo watch + wasm-pack build 자동화 |
| 공개 배포 | **GitHub Pages + GitHub Actions** | `main` 푸시 시 release WASM과 Vite 앱을 빌드하여 `https://idgmatrix.github.io/sonar-war/`에 공개 |
| 시뮬레이션 루프 | 고정 시간 스텝 **10Hz** (렌더는 60fps 보간) | 물리 결정론성 확보, 네트워크 동기화 기준이 됨 |
| 오디오 DSP | **Rust/WASM DSP 코어 (AudioWorklet 호스트) + Web Audio API (보조)** | Rust: 해양 잡음 합성, 엔티티 소음 합성(토널/캐비테이션/DEMON/도플러), **풀 지연-합 빔포밍**. Web Audio: 출력 경로, 사후 필터링(무전기 FX 등), 게인/라우팅만 담당 |
| 소나 디스플레이 | **2D Canvas 먼저, WebGPU 후발** | BASS/LOFAR 워터폴은 스크롤링 이미지라 2D Canvas가 충분하고 반복이 빠름. WebGPU는 PDF 클라우드 셰이더와 성능 병목 발생 시 도입 (명세서 Phase 2 대응) |
| 전술 맵 | 2D Canvas (와이어프레임/등고선) | Three.js 3D 뷰는 마지막 옵션 (명세서의 선체 와이어프레임 뷰) |
| 음성 | Web Speech API + Web Audio 무전기 필터 FX | 코파일럿 (M7) |
| 멀티플레이 | **PeerJS** (DataChannel, `ordered:false, maxRetransmits:0`) | 시그널링은 PeerJS 클라우드 + SDP 복사/붙여넣기 폴백 |
| 테스트 | Vitest (TS) + **cargo test** (Rust) | 음향 물리/DSP 코어는 Rust 네이티브 테스트로 빠르고 정밀하게 검증 (M1~M2) |

**WebGPU 도입 시점 판단 기준:** 2D Canvas 워터폴이 프레임 드롭을 일으킬 때, PDF 클라우드가 셰이더로만 표현 가능한 밀도로 올라갈 때. 그 전에는 Canvas 2D로 간다.

각 마일스톤은 기능 구현만으로 닫지 않고 `npm test`, `npm run wasm:test`,

`npm run wasm:build`로 브라우저용 산출물을 재생성하고, 오디오 완료 기준은
localhost Chromium에서 별도의 수동 인수 검사를 남긴다.

### 지속 배포 및 공개 검증

- 공개 소스 저장소에서 GitHub Pages 사이트를 함께 공개한다. 저장소 공개 전환에 따라
  GitHub Free에서도 Pages를 사용할 수 있다.
- `main` 푸시와 수동 실행 시 GitHub Actions가 TS/Rust 테스트 → release WASM →
  Pages 전용 Vite 빌드 → `dist/` 배포 순서로 실행한다.
- 로컬 개발 base는 `/`, Pages 빌드 base는 `/sonar-war/`로 분리한다.
- 배포된 JavaScript/WASM/정적 자산은 공개된다는 점을 전제로 하며 비밀값이나 비공개
  원시 데이터는 클라이언트 번들에 포함하지 않는다.
- **완료 기준:** 공개 URL에서 첫 사용자 입력 후 AudioWorklet과 WASM이 로드되고,
  BASS/LOFAR 화면, 장면 전환, 오디오 출력이 localhost와 동일하게 동작한다.

## 3. 코드 구조

```
sonar-war/
├─ dsp-core/            # ★ Rust DSP 크레이트 (wasm32 + 네이티브 듀얼 빌드)
│  ├─ src/
│  │  ├─ source/        # 발생원 자체의 원시 신호: 추진·기계·캐비테이션·생물음 등
│  │  ├─ propagation.rs # 거리/흡수·음속 구조·도플러·배열 도달 지연
│  │  ├─ receiver.rs    # 하이드로폰 교정·주변 소음·배열·빔포밍
│  │  ├─ noise/         # 해상 상태·선박 밀도 등에 따른 주변 환경 소음장
│  │  ├─ analysis.rs    # BASS 및 향후 LOFAR/DEMON용 읽기 전용 신호 분석
│  │  ├─ offline.rs     # 네이티브 WAV/계층 trace/블록 통계 직렬화
│  │  ├─ output.rs      # 최종 출력 제한
│  │  ├─ physics/       # 계층이 공유하는 물리식과 단위 변환
│  │  └─ lib.rs         # wasm_bindgen 바인딩: 장면/해양/빔 설정 + process(out) + 표시 텔레메트리
│  └─ tests/            # cargo test (물리/DSP 단위 테스트, 네이티브 실행)
├─ src/
│  ├─ core/
│  │  ├─ entity/        # AcousticEntity (공용 음향 상태), exportState/importState
│  │  ├─ sim/           # 월드 상태, 10Hz 틱 루프, 자함 동역학(조타/트림/스로틀)
│  │  ├─ sensors/       # 어레이/빔 조향 상태 (DSP 연산은 dsp-core에 위임)
│  │  └─ tma/           # 베어링-온리 파티클 필터, PDF 클라우드 샘플
│  ├─ dsp/
│  │  └─ worklets/      # AudioWorklet 호스트: WASM 로드, 재사용 Float32Array 경계,
│  │                    #   WASM 출력 → 출력 채널 복사 + 저주기 표시 텔레메트리
│  ├─ render/
│  │  ├─ displays/      # BASS 워터폴, LOFAR 스펙트로그램, 빔 인디케이터 (2D Canvas)
│  │  └─ map/           # 전술 맵, PDF 클라우드 렌더러
│  ├─ ui/               # CRT 테마(4종), 통신 로그, 제어 패널, 옵션
│  ├─ audio/            # Web Audio 출력 경로: 게인/라우팅, 사후 필터(무전기 FX), 스퀠치
│  ├─ game/             # 시나리오(해저 지형+SVP 맵), 스크립트 타겟, 승패 조건
│  └─ net/              # (M8) PeerJS 연결, 2~5Hz 상태 브로드캐스트, 이벤트 메시지
├─ docs/                # 설계 문서 + 본 계획
├─ data/acoustics/      # 소스·환경·수신기별 근거 있는 파라미터 프로파일
└─ tests/               # TS 단위 테스트 (시뮬레이션/UI)
```

`source/`, `propagation.rs`, `receiver.rs`, `analysis.rs`, `output.rs`는 실제 샘플 경로에
적용되었다. `offline.rs`는 같은 엔진 경로를 네이티브에서 추적한다. 이후 세분화에서도
디렉터리 형태보다 계층별 입출력 계약과 독립 검증을 우선한다.

## 4. 핵심 데이터 구조

```ts
// 모든 잠수함/표적/어뢰/미끼가 공유하는 단일 음향 엔티티
interface AcousticEntity {
  id: string;
  kind: 'sub' | 'torpedo' | 'decoy';
  position: [number, number, number];   // x, depth, z (m, 수심은 +down)
  velocity: [number, number, number];
  heading: number;                      // rad
  rpm: number;                          // 스크루 회전수
  cavitation: number;                   // 0~1 광대역 레벨
  tonals: number[];                     // Hz, LOFAR 토널 (기계 고조파)
  bladeRate: number;                    // Hz, DEMON 복조 주파수 (RPM×엽수/60)
  sourceLevels: { broadband: number; tonal: number[] }; // dB
  towedArrayDeployed: boolean;
}

// 네트워크 페이로드 (2~5Hz, 수십 바이트) — WebRTC 문서의 acousticState와 1:1 대응
exportState(): { pos, vel, hdg, spd, rpm, cav, tonals, bladeRate, towed }
importState(data): void
```

- **TL 룩업 그리드:** 맵(해저 지형 + 수온약층)이 정해지는 시나리오 시작 시,
  `(거리 × 발신 수심 × 수신 수심 × 주파수 대역)` 격자로 TL 테이블을 **미리 계산**해 두고
  시뮬레이션 중에는 조회만 한다. 프레임당 레이 트레이싱을 피하는 핵심 최적화.
- **음영 구역:** 같은 그리드에서 전달 불가 영역을 플래그로 저장 → TMA PDF 클라우드에서
  "안개가 깎이는" 영역으로 사용.

### 4.1 음향 파라미터 데이터 원칙

각 파라미터 프로파일은 최소한 다음 메타데이터를 가진다.

- 값과 단위, 유효 범위 또는 확률 분포
- 측정 기준 조건(거리, 주파수 대역, 속력/RPM, 수심, 해상 상태 등)
- 출처와 접근일, 적용 대상, 모델 변환 과정
- 불확실성과 신뢰도: **A**(직접 측정·표준), **B**(문헌 기반 유사체·경험식), **C**(게임용 가정)
- C 등급 값은 코드에 숨은 매직 넘버로 두지 않고 데이터에서 식별·교체할 수 있어야 한다.

### 4.2 수중 음향 소스 카탈로그

`docs/수중 음향 소스 카탈로그.md`를 만들고 아래 분류별로 재현할 구체 소리, 생성 모델,
필요 파라미터, 공개 근거, 구현 우선순위를 관리한다.

| 분류 | 재현 대상 예시 | 초기 우선순위 |
|---|---|---:|
| 함정 추진·기계 | 축 회전, 블레이드 통과 주파수, 감속기/모터/펌프, 캐비테이션 | P0 |
| 전투·능동 음향 | 능동 소나 핑, 어뢰 추진음, 디코이, 폭발·충격 과도음 | P0–P1 |
| 상선·수상 활동 | 상선 프로펠러, 고속정, 저주파 선박 교통 소음 | P0–P1 |
| 자연 환경 | 파랑·바람·강우, 열잡음, 얼음, 지진·화산 | P0–P2 |
| 생물 | 고래류, 돌고래 클릭, 어류·갑각류 집단음 | P2 |
| 산업·기타 | 시추, 파일 항타, 준설, 케이블/장비음 | P2–P3 |

P0는 핵심 게임 루프에 필요하며 공개 파라미터로 우선 검증할 소리다. 군용 플랫폼의
실제 서명처럼 공개 자료가 부족한 경우 민간 선박·일반 기계·공개 측정치의 유사 모델을
사용하고 B/C 등급임을 명시한다.

  `process()` 스텁이 WASM으로 브라우저에서 실행되는 것 확인
- 10Hz 고정 틱 루프 + 60fps 렌더 루프 분리
- `AcousticEntity` + `exportState`/`importState` 구현
- HTML 셸 + Classic P31 Green 테마 플레이스홀더
- **완료 기준:** 빈 화면에 시계(틱 카운터)가 10Hz로 뛰고, 엔티티 직렬화 왕복 테스트 통과,
  WASM 스텁이 AudioWorklet에서 호출되어 44.1kHz 정현파가 스피커로 출력됨.

### M1 — 음향 물리 코어 (dsp-core/Rust) (2~4일)
- 소나 방정식: `SNR = SL − TL − (NL − DI)`, `SE = SNR − DT`
- TL: `20log₁₀R + α(f)·R` (Thorp 흡수 근사), TL 룩업 그리드 + 음영 구역 플래그
- NL: Coates/Wenz 난류·원거리 선박·바람·열잡음 공학 근사 + 강우 옵션
- 수온약층: 깊이-수온 프로파일 → 음속 프로파일(맥켄지 근사) → 그리드 계산
- 전부 `dsp-core` Rust 크레이트에 구현 — DSP와 같은 언어/테스트 체계
- **완료 기준:** `cargo test`로 "거리/수심/주파수별 SNR·SE 값이 수식과 일치",
  "약층 아래 표적이 음영 구역에 들어감에 따라 SE가 임계 이하로 떨어짐" 검증.

### M2A — DSP 실행 기반 (Rust/WASM + AudioWorklet) (완료)
- **dsp-core (Rust):**
  - 해양 배경잡음 합성 (당시 1-pole 기준선; M2B에서 Coates/Wenz 목표 PSD로 교정)
  - 엔티티 소음 합성: 토널(LOFAR 라인) + 캐비테이션 광대역 + **DEMON 변조**
    (캐비테이션 포락선을 bladeRate로 AM) + 도플러 시프트(상대 속도 기반)
  - **풀 지연-합 빔포밍** (명세서 3.2의 τᵢ = pᵢ·û/c 그대로 구현) —
    Rust/WASM이라 구형 배열의 실시간 풀 지연-합이 가능. 성능 여유 확인 후
    빔 수/채널 수로 튜닝
  - `cargo test`로 물리/음향 연산 검증 (M1의 물리 코어도 이 크레이트에 통합)
- **AudioWorklet 호스트 (TS):** WASM 로드, 재사용 `Float32Array`로 출력 블록을
  받고 장면/해양/빔 파라미터는 블록 경계에서 메시지로 반영, worklet 출력 → AudioContext 연결
- Web Audio API는 출력 경로(게인/라우팅/사후 필터)로만 사용
- **완료 기준:** 표적을 거리/수심별로 배치했을 때 LOFAR 토널 + 광대역이 들리고,
  RPM 변화가 들리며, 접근/이탈 시 도플러가 들림. worklet CPU 점유가
  프레임 예산(10ms)의 50% 미만.

> M2A의 완료는 **실시간으로 합성 가능한 엔진과 호스트 경로가 작동한다**는 뜻이다.
> 각 음원이 실제 녹음과 유사하도록 파라미터가 조사·교정되었다는 뜻은 아니다.

**목표:** 소스·전파·수신 모델을 독립적으로 교체하고 검증할 수 있는 구조를 만들고,
P0 음원에 근거 있는 기준 파라미터를 적용한다.

**구현 항목**

- [x] `docs/수중 음향 소스 카탈로그.md`와 기계 판독 가능한 음향 프로파일 스키마 작성
- [x] 모든 프로파일에 단위·기준 조건·출처·불확실성·신뢰도 등급 기록 및 자동 검증
- [x] Source → Propagation → Receiver 스펙트럼·단위 계약과 상태형 샘플 버퍼를 실제 엔진 경로에 적용
- [x] 수신기 배열을 시간축 전진 없이 읽는 BASS Analysis 계층과 출력 제한 계층 분리

- [x] 상선 31대역별 Thorp 흡수·거리 TL 적용 및 1 km 합성 PSD `±2.5 dB` 골든 검증
- [x] 단일 벌크선 140 RPM 측정점의 블레이드율·엔진 점화율·발전기 15개 톤을 별도 오버레이로 구현하고 다른 운항점 외삽 차단
- [x] 협대역 소스 레벨을 RMS 음압으로 해석하도록 정현파 피크 진폭의 `√2` 변환을 적용하고 회귀 골든 갱신

- [x] Coates/Wenz 목표 PSD 수식 회귀 및 결정적 1/3옥타브 합성 결과의 대역별 ±2 dB 검증
- 최소 음속 구조 채널 검증. 표면/해저 반사·다중 경로는 계산 비용별 품질 단계로 설계
- [x] 결정적 오프라인 WAV 렌더러와 계층별 블록 덤프 도구 제공

- 톤 레벨·대역 에너지·채널 임펄스 응답 골든 테스트 추가

**완료 기준**

- P0 음원 각각에 소스 프로파일, 근거, 신뢰도, 허용 오차가 존재할 것
- 동일한 원시 소스에서 환경 프로파일만 바꾸면 전파 결과만, 수신기 프로파일만 바꾸면 센서 결과만 달라질 것
- 대표 장면의 합성 스펙트럼이 문헌·표준에서 도출한 목표 곡선과 문서화된 허용 오차 안에 들 것
- 출처나 C 등급 표시가 없는 조정 상수가 DSP 경로에 새로 추가되지 않을 것
- 기존 결정성, WASM 동작, 블록당 5 ms CPU 예산을 유지할 것

### M3 — 소나 디스플레이 (BASS / LOFAR) (3~5일)

M3-1 화면 프로토타입은 구현되어 있으나 표시 신호의 최종 의미와 합격 기준은 M2B의
수신기/분석 계층 계약을 적용한 뒤 확정한다.
- 센서 대역을 분리한다. BASS는 구형/플랭크 배열의 광대역 방위 탐지,
  LOFAR는 예인 선배열(TAS)의 10~500Hz 협대역 분석을 사용한다. 8.4m 구형 배열만으로
  수십 Hz 토널의 방위 선택성이 생긴다고 가정하지 않는다.
- LOFAR: **Rust가 합성한 조향 빔 오디오만** `AnalyserNode`로 관측해 주파수-시간
  스펙트로그램 워터폴(2D Canvas)과 고조파 자(Harmonic Ruler)를 표시한다.
- BASS: Rust DSP가 동일한 하이드로폰 링 버퍼를 시간축을 전진시키지 않고 여러 방위로
  읽어 5° 간격 전 방위 광대역 레벨을 저주기 텔레메트리로 제공하고, Canvas는
  레벨-시간/방위 워터폴만 그린다. TS에서 음향 신호를 재합성하지 않는다.
- 빔 조향 UI: BASS 클릭/방위·앙각 슬라이더 → 주 오디오 빔과 커서를 함께 갱신한다.
- **완료 기준:** BASS에서 알려진 표적 방위의 연속 궤적이 보이고, 그 방위를 클릭해
  조향할 때 LOFAR 토널이 선명해지며, 고조파 자로 기본 주파수를 판독할 수 있다.
  M3 스캔을 켠 상태에서도 worklet CPU 상한이 `<5ms/block`이어야 한다.

**구현 체크포인트:** 전 방위 BASS와 Canvas/조향/고조파 자까지를 M3-1로 두고,
TAS 배열 모델과 센서 선택, 알려진 방위 정합/비정합 LOFAR 레벨 회귀 검증을 M3-2로 둔다.
M3-2 전에는 “조향 시 저주파 토널이 선명해짐” 완료 기준을 충족한 것으로 판정하지 않는다.

### M4 — 자함 동역학 + 싱글 플레이 (2~4일)

- RPM-속도 커플링 → 소음 모델 연동, 캐비테이션 모델(속도-선체)

### M5 — TMA + PDF 클라우드 (4~7일)

- **완료 기준:** 변침 전 방위선 방향 수십 km 길쭉한 안개 → 변침 후 좁고 밝은 코어로 응축되는
  과정이 시각적으로 확인된다.

- **완료 기준:** CADET 레벨 안내를 켠 채 처음 플레이하는 사람이 M6 루프를 완주할 수 있다.

### M8 — 멀티플레이 (WebRTC) (3~5일)
- PeerJS 연결, 방 코드(예: `BLACKTIDE-7X9`) + 초대 링크, **SDP 텍스트 복사 폴백 모드**
- 2~5Hz `acousticState` 브로드캐스트 (WebRTC 문서의 JSON 페이로드 그대로)
- 이벤트 메시지: 능동 핑 / 어뢰 사출 / 디코이 전개 (즉시 전송)
- 상대 엔티티는 `importState()`로 주입 — **게임 코드는 1줄도 안 건드린다** (개발 지침 검증)
- **완료 기준:** 브라우저 두 대가 초대 코드로 접속해 M6 듀얼을 완료한다.

**총 예상: 약 30~50일 + 음향 자료 조사 변동 (1인 기준, M2B 추가분 반영).**

## 7. 즉시 다음 단계

1. **상선 톤 골든 분석:** 140 RPM 유사체의 원시·전파 후 톤 주파수와 준위를 문헌 기반 허용 오차로 검사한다.
2. **방향성 경계:** 저주파 쌍극자와 주파수별 유효 소스 수심을 임의 보정 없이 표현할 Source/Propagation 계약을 설계한다.
3. **최소 음속 구조 채널:** 수심에 따른 직접 경로·음영 구역이 대역별 결과에 반영되는지 검증한다.
4. **P0 기준 모델 교정:** 상선·잠수함 유사체·어뢰 유사체·주변 소음 순으로 파라미터를 적용하고 허용 오차와 CPU 비용을 기록한다.
5. **M3-2/M4 재개:** 사실성 기준선과 월드→DSP 어댑터가 안정된 뒤 TAS와 수중 운동학을 연결한다.
